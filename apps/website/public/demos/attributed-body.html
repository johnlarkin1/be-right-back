Inside an attributedBody blob

When a message isn't in the text column, it's a serialized NSAttributedString in attributedBody — Apple's old NSArchiver "streamtyped" format. Type a message and watch the bytes Apple actually writes to disk, then watch the decoder find your text inside them.

tl;dr

The blob is a length-prefixed walk of an Objective-C object graph: streamtyped magic → the class hierarchy (NSAttributedString → NSObject → NSString) → a + marker, a length byte, and finally your text → then an NSDictionary of attribute runs. For short messages the framing dwarfs the payload — that's why a 5-char message costs ~180 bytes.

What's faked vs real: the framing here is a faithful, slightly-trimmed streamtyped layout — real NSArchiver blobs carry the same magic, the same length-prefixed class names, the same 0x2b C-string marker, and an NSDictionary of attribute runs, but a real attribute run also encodes ranges and style objects we abbreviate. Long strings (≥128 bytes) really do switch to the multi-byte length encoding shown. The decode walk is exactly what the Rust code does via Apple's runtime.

Where this shows up in BRB: crates/messages-db decodes this through Objective-C FFI (NSUnarchiver for the streamtyped variant), falling back through NSKeyedUnarchiver modern and legacy APIs. Once any unarchiver succeeds, [attributedString string] yields the green bytes above.
