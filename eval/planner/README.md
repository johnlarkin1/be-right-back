# Query Planner Eval

Benchmarks Casper's date-range extraction: the **regex** planner
(`crates/ingestion/src/query_planner.rs`), a small **LLM** doing structured
extraction, and the shipped **hybrid** policy (regex-first, LLM-fallback) in
`crates/inference/src/agent/planning.rs`.

## Why

The regex planner is exact on the calendar phrasings it has unit tests for, but
**silently returns no date filter on natural paraphrases** ("first quarter of
2025", "over the holidays", "when covid started"). A small local model extracts
those reliably. The hybrid keeps regex authoritative (so in-distribution stays
perfect) and only calls the LLM when the regex finds no range *and* the query
mentions time (`temporal_hint`).

## Dataset

`dataset.json` — 31 labeled queries against a fixed `now = 2026-02-09`:
- **Set A** (19): phrasings the regex has tests for. Regex = 100% by construction.
- **Set B** (12): paraphrase / world-knowledge the regex was never built for.
- `match`: `crisp` (exact day), `fuzzy` (range overlap), `none` (must abstain).

## Run

```bash
make eval-planner                 # regex + 9B LLM + live hybrid, then score
make eval-planner MODEL=mlx-community/Qwen3.5-4B-4bit TAG=4b
```

Or step by step:

```bash
cargo run -p ingestion --example plan_dump                                  # -> regex_out.json
HF_HUB_OFFLINE=1 ~/.be-right-back/mlx-venv/bin/python eval/planner/run_llm_planner.py <model> <tag>  # -> llm_out_<tag>.json
cargo run -p inference --example plan_eval -- <model> <tag>                  # -> llm_out_hybrid_live_<tag>.json (real Rust path)
~/.be-right-back/mlx-venv/bin/python eval/planner/score.py regex_out.json llm_out_<tag>.json llm_out_hybrid_live_<tag>.json
```

`score.py` also synthesizes a `hybrid_<tag>` column offline (merging
`regex_out` + `llm_out_<tag>` by the exact policy) so the live Rust result
(`hybrid_live_<tag>`) can be checked for parity against the expected ceiling.

## Results (committed snapshot, now=2026-02-09)

`hybrid_live_9b` is the **real Rust path** (`resolve_turn_plan` via the daemon);
`hybrid_4b` is the offline-simulated merge for the 4B tier.

| run | Set A (19) | Set B (12) | Overall (31) |
|---|---|---|---|
| regex (before) | 100% | 17% | 68% |
| 9B LLM alone | 74% | 75% | 74% |
| **hybrid_live_9b (after)** | **100%** | **75%** | **90%** |
| hybrid_4b (simulated) | 100% | 58% | 84% |

Set A stays at 100% (regex authoritative); Set B more than quadruples. With
thinking suppressed (`enable_thinking=false` now genuinely disables CoT in the
daemon), the planner call averages ~0.3s and only fires on regex-misses.

## Known limitation

The hybrid can score *below* the pure LLM on Set B when the regex **mis-fires** —
e.g. "summer before last" matches a bare "last" recency window, so the regex
produces a (wrong) range and the LLM is never consulted. Regex-first is still a
large net win and never regresses Set A; tightening recency-only mis-fires is
future work.

## Files

- `dataset.json` — labeled cases
- `run_llm_planner.py` — LLM extraction (takes model id + tag)
- `score.py` — scorer + synthesized hybrid column
- `regex_out.json`, `llm_out_4b.json`, `llm_out_9b.json` — reference snapshots
- `REPORT.md` — full per-case tables (regenerated by `score.py`)

- live hybrid: `crates/inference/examples/plan_eval.rs`
