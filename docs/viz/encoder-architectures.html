How BRB uses bi-encoders and cross-encoders

A from-first-principles tour of the two transformer architectures sitting at the heart of search — what they actually compute, why we need both, and how they cascade in the BRB pipeline.

tl;dr

A bi-encoder turns each chunk into a single 768-dim vector once, at ingest time, before any query exists. It's cheap because we precompute every chunk's vector and use an HNSW index to find nearest neighbors in milliseconds — but lossy, because the model has to compress the chunk without knowing what we'll ask about it.

A cross-encoder takes a (query, chunk) pair, concatenates them into one input sequence, and runs the model on the pair together. Attention can now flow between query and document tokens, so the model actually reads the document while looking at the query. The score it outputs is query-conditional — same document, different query, different score.

BRB uses the bi-encoder to retrieve ~30 candidates out of 250K chunks fast (recall), then runs the cross-encoder over those 30 to re-rank them precisely (precision). You can't afford the cross-encoder over 250K. You can't afford the precision loss of bi-encoder alone.

1.The problem we're solving

We have ~250K chunks of iMessage history in DuckDB, each with a 768-dim embedding vector attached. A user types a natural-language query — say "thanksgiving turkey" — and we need to find the chunks most relevant to that query, fast enough for an interactive feel.

Phrased generally: we want a function 

score(query, document) → ℝ

that tells us how relevant a given document is to a given query. We're going to sort the 250K chunks by this score and return the top-K.

There's a brutal trade-off lurking in how we build that function:

  • If the function looks at query and document jointly (i.e., runs a neural network on the pair together), it can be smart and precise — but we have to run the network fresh for every (query, doc) pair. With 250K docs and a model that takes ~5ms per pair, that's 20+ minutes per query. Unusable.
  • If the function only looks at each side separately (i.e., encodes query and doc into vectors and compares those), we can precompute every document's vector once, store them in a vector index, and answer a query in milliseconds. But the model never sees them together — it has to commit to a single representation of each side before knowing the other. Lossy.

These are not just engineering trade-offs — they correspond to two fundamentally different model architectures: bi-encoders (also called late-fusion or dual encoders) and cross-encoders (also called early-fusion rankers). To understand why they have these properties, we need to peek inside a transformer encoder for a minute.

2.What's inside a transformer encoder

Both the bi-encoder (ModernBERT) and the cross-encoder (MiniLM) we use are BERT-family transformer encoders. They have the same internal structure — the difference is in how we feed inputs into them and read outputs out of them, not in the architecture of the layers themselves.

A transformer encoder is a stack of identical "encoder layers." Each layer takes in a sequence of token vectors and outputs a sequence of token vectors of the same length and dimension:

A single transformer encoder layer. The whole stack just repeats this L times.

The single most important operation inside each layer is the multi-head self-attention block. Mechanically, for every token in the input sequence, attention computes a weighted average of every other token's representation, where the weights are learned via three linear projections (Query, Key, Value): 

attention(Q, K, V) = softmax(QKᵀ / √d_k) · V

The crucial property: every token can attend to every other token in the input sequence. If two tokens are in the same forward pass, they can influence each other's representations through attention. If they're in different forward passes, they can't — they live in separate sequences and there is no architectural mechanism for them to exchange information.

key insight

The entire bi-encoder vs cross-encoder distinction comes down to this one fact: are the query tokens and document tokens in the same forward pass, or in two separate forward passes? Everything else — the speed, the quality, the precomputability — follows from that single choice.

3.The bi-encoder architecture

A bi-encoder runs the model twice: once on the query alone, once on the document alone. Each side gets compressed into a single fixed-size vector (typically by taking the [CLS] token's final hidden state, or by mean-pooling over all token outputs). Then the two vectors are compared via cosine similarity at the very end.

Two forward passes through (the same) model, each one isolated from the other. The vectors only meet at the very end, after each side has been compressed to a single point.

What this actually computes

Strip the visuals away and the bi-encoder computes: 

v_q = encode(query)             # 768-dim vector, run once per query
v_d = encode(document)          # 768-dim vector, run once per doc — PRE-COMPUTED at ingest
score = cos(v_q, v_d)             # scalar in [-1, 1]

Two structural properties fall out of this:

  1. Document vectors can be precomputed. encode(document) doesn't depend on the query, so we run it once at ingestion time, store the result, and never recompute it. The 250K chunk vectors sit in a DuckDB table; querying just means a single encode(query) + a nearest-neighbor lookup.
  2. The document representation cannot adapt to the query. The same document gets the same vector no matter what we ask. If the chunk talks about both Boston traffic and 6am departures, that's all crammed into one 768-dim point — and we can't ask the model to highlight one half over the other depending on what the user wants.

What BRB uses

Our bi-encoder is nomic-ai/modernbert-embed-base, in its MLX-quantized 8-bit form: mlx-community/nomicai-modernbert-embed-base-8bit. It's a 22-layer ModernBERT encoder, fine-tuned with contrastive objectives so that cosine similarity in its output space corresponds to semantic relatedness. Outputs a 768-dim vector per document.

The actual call (from the Python entry script that Rust spawns as a subprocess):

from mlx_embeddings import load, generate

model, tokenizer = load("mlx-community/nomicai-modernbert-embed-base-8bit")

# run the model — single forward pass, 768-dim output
embedding = generate(model, tokenizer, texts=[query_text])

At ingest time, the same model gets called over all chunks in batches; the resulting 768-dim vectors get inserted into DuckDB with an HNSW index over them. Query time = embed the query (~50ms warm, ~2s cold) + HNSW lookup (~5–15ms). That's how we can do nearest-neighbor over 250K chunks in well under a second.

4.The cross-encoder architecture

A cross-encoder concatenates the query and the document into a single token sequence — joined by special [CLS] and [SEP] tokens — and runs the model on the pair together, as a single forward pass. The output is a single scalar relevance score.

One forward pass. The model sees both inputs at once and outputs a single relevance number.

What this actually computes

score = encode_and_classify(query, document)
       # inputs are concatenated into ONE sequence:
       # [CLS] query_tokens [SEP] document_tokens [SEP]
       # model output is a single scalar, not a vector

The structural consequences are the mirror image of the bi-encoder's:

  1. Nothing can be precomputed. Because the document's representation now depends on the query (via cross-attention), we can't compute "the document's score" ahead of time. We have to run the full model fresh for every (query, document) pair we want to score.
  2. The document representation is query-aware. Attention layers can dynamically decide which parts of the document matter for this specific query. Same chunk, different query → different attention pattern → different score.

What BRB uses

Our cross-encoder is cross-encoder/ms-marco-MiniLM-L-6-v2: a 6-layer distilled BERT (22M params), fine-tuned on MS MARCO passage relevance. MS MARCO is ~1M real Bing queries paired with labeled relevant passages from an 8M-passage corpus — the canonical "is this passage relevant to this query?" benchmark. The training objective makes the model output high logits for relevant pairs and low logits for irrelevant ones.

The actual call (in mlx/src/ml/reranker.py):

from sentence_transformers import CrossEncoder

class CrossEncoderReranker:
    DEFAULT_MODEL = "cross-encoder/ms-marco-MiniLM-L-6-v2"

    def _ensure_loaded(self):
        self._model = CrossEncoder(self.model_name)

    def rerank(self, query: str, candidates: list):
        pairs = [(query, c.text) for c in candidates]
        scores = self._model.predict(pairs)   # one forward pass per pair, batched
        return sorted(zip(candidates, scores), key=lambda p: -p[1])

The Rust side (in crates/ingestion/src/rerank.rs) wraps this in a subprocess call so the embedding / search path doesn't have to know Python is involved. It's also wrapped in best-effort error handling — if the model fails to load or the subprocess crashes, we fall back to the pre-rerank order rather than erroring out.

5.The actual mechanical difference: attention

Here's the diagram that, for me, makes everything click. An attention matrix shows which input tokens attend to which other input tokens in a self-attention layer. For a sequence of length N, this is an N×N matrix where row i, column j represents "how much token i attends to token j" (after softmax, these rows sum to 1).

When we lay out the attention matrix for a (query, document) pair, it naturally splits into four quadrants:

The bi-encoder is missing the Q→D and D→Q quadrants. That's the entire structural difference — and it's why the cross-encoder is strictly more expressive but strictly more expensive.

In the bi-encoder, the Q→D and D→Q blocks do not exist in the computation. There is no operation anywhere in the forward pass where a query token's attention output depends on a document token. The model literally cannot combine information from both sides until we take cosine similarity at the very end — and by then, both sides have been compressed to a single point.

In the cross-encoder, those Q→D and D→Q quadrants are populated and learnable. This is what lets the model say things like "this 'turkey' token in the document is talking about the same thing as 'turkey' in the query, and it's in a thanksgiving context, so it's relevant". Attention weights inside those blocks carry the relevance signal.

6.Why we need both

Now we can write down the trade-off concretely:

Input to model query or doc (two passes) query and doc together (one pass)

Doc representation depends on query? no yes
Pre-compute doc vectors offline? yes no
Cost per query, 250K docs ~15ms total
(1 encode + HNSW lookup)		 ~20+ min
(250K full forward passes)
Cost per query, 30 docs N/A — you'd just use it directly ~100ms
(30 batched passes)
What it's good at Broad topical retrieval (recall) Fine-grained relevance ranking (precision)
Failure modes Misses query-specific nuance: negation, distractors-in-context, ambiguous polysemes Doesn't scale to large corpora

Neither model is a strict superset of the other. The bi-encoder is a worse scorer than the cross-encoder, but it's the only one that scales. The cross-encoder is a much better scorer, but it's the only one that can't be precomputed. The cascade pattern — bi-encoder narrows the field, cross-encoder picks the winner — gets you the best of both.

the right mental model

Don't think of cross-encoder as "a better embedding model." Think of it as a different category of model entirely. It doesn't produce embeddings at all — it produces relevance scores. You can't store its output in a vector index. You can't take cosines of its outputs. It's a scoring function over pairs, not a representation function over items.

7.BRB's full pipeline end-to-end

Now let's trace what actually happens when you type a query in the BRB desktop app and hit search. The whole flow lives in crates/ingestion/src/search.rs (the hybrid_search function). Here it is at a glance:

The bi-encoder shows up at step 2 (embed query) and implicitly at every chunk vector in DuckDB. The cross-encoder shows up at step 6, scoring the ~30 candidates the cheaper pipeline narrowed down to.

Two distinct uses of the bi-encoder

Notice that ModernBERT is used in two places in this pipeline, and they look different but are the same model:

  • At ingest time: every chunk in the user's iMessage history gets embedded once, and the resulting 768-dim vector is inserted into DuckDB with an HNSW index built over it. This happens once per user, takes a long time (minutes for 250K chunks), and only re-runs when new messages come in.
  • At query time: only the query needs to be embedded — the chunk vectors are already in the index. One forward pass through the model + an HNSW lookup gives us the candidate set in ~15ms.

This split is only possible because the bi-encoder is, well, a bi-encoder. If it were a cross-encoder, the chunk's representation would depend on the query, and we'd have to re-run the model for every chunk on every query. That's the precomputability argument made flesh.

8.Worked example: "thanksgiving turkey"

Let's trace a real query through the pipeline. (Numbers below are pulled from the actual brb search "thanksgiving turkey" --breakdown output, which exposes per-ranker rankings before the merge.)

Step A — embed the query

We run encode("thanksgiving turkey") through ModernBERT once and get a 768-dim vector. That's the bi-encoder doing its job. We never touch the cross-encoder yet.

Step B — semantic candidate retrieval (HNSW lookup)

We ask DuckDB for the 45 chunks whose stored 768-dim vectors have the highest cosine similarity with our query vector. This is a logarithmic-time graph traversal over the HNSW index, not a brute-force scan. Some of what comes back:

semantic rankchunknote
1chunk 172774 (2015, "happy thanksgiving you fricking turkey")literal token match
2chunk 172415 (2024, "cooked an entire thanksgiving meal")semantically dead-on
4chunk 175976 (2019, "Happy thanksgiving!! …")also dead-on
19chunk 181896 (2020, covid + thanksgiving thread)topical but indirect

Notice the bi-encoder ranks chunk 172774 (a 2015 greeting) and chunk 172415 (a 2024 cooking comment) very highly. It has no way to know that we likely want recent results, or that "thanksgiving turkey" as a query is more about thanksgiving plans/meals than about wishing someone happy thanksgiving — those are nuances that require reading the query and the chunk together, which the bi-encoder structurally cannot do.

Step C — BM25 + ilike run in parallel, RRF merges them with the semantic ranks

By the end of step 5 we have ~30 deduplicated candidates ordered by RRF-fused rank (with a small recency boost). Each candidate is a chunk that one or more of the three retrievers liked.

Step D — cross-encoder rerank

Now the cross-encoder gets to work. For each of the 30 candidates, we construct the input: 

[CLS] thanksgiving turkey [SEP] <chunk text — up to ~512 tokens> [SEP]

We batch all 30 into one tensor and call self._model.predict(pairs), which runs the 6-layer MiniLM forward pass over the entire batch. Each pair gets a single scalar logit. We sort descending.

This is where the cross-encoder earns its keep. When MiniLM sees: 

[CLS] thanksgiving turkey [SEP] Me: happy thanksgiving you fricking turkey
                                Simon: ❤️ thanks studd, happy thanksgiving [SEP]

…it can use attention to notice that the document's "turkey" is a vocative (used as a nickname for the recipient), not a noun referring to the bird. That's the kind of compositional, query-conditional judgment a bi-encoder structurally cannot make — the bi-encoder just saw two strings with "turkey" in them and called them similar.

Conversely, when MiniLM sees a chunk about "I am making turkey for Thanksgiving dinner — what's your stuffing recipe?", every attention head can light up the cross-block: "turkey" here is the noun, "thanksgiving" here is the holiday, and they're in the right relationship to the query. High score.

The resulting reordering tends to push semantically-precise chunks up and demote distractor chunks down — even when both shared similar bi-encoder vectors. That's the whole point.

Bi-encoder: mlx-community/nomicai-modernbert-embed-base-8bit (768-dim, 22-layer ModernBERT)
Cross-encoder: cross-encoder/ms-marco-MiniLM-L-6-v2 (22M params, 6-layer distilled BERT, MS MARCO fine-tuned)
